# Разбор двух отчётов Game Debug 1.1

## Итог

Новые профили решили проблему предыдущего сбора: **CorePackages отсутствует, лимиты обхода и исходников не сработали**. Получены основные общие конфиги и клиентские контроллеры игры.

Но найдена важная оговорка: **два результата декомпиляции содержат только сообщение об ошибке**. Сборщик 1.1 засчитал их как полученный текст. Поэтому `sourceFailures: 0` и `incomplete: false` не означают, что все исходники восстановлены корректно.

Данные: PlaceId `122287678911982`, UniverseId `10764019529`, версия места `2812`. Два снимка сделаны 25 сентября 2026 в 12:49:19 и 12:51:52 UTC. Это разные моменты времени, не единый атомарный снимок игры.

## 2. Найденная проблема декомпиляции

Оба пути находятся в PlayerGui локального игрока:

- `TEAMS.WitchesPC.Powers1.PowerController`
- `TEAMS.WitchesCONSOLE.Powers1.PowerController`

Вместо кода возвращено:

```text
-- Error: :5: Expected identifier when parsing expression, got 'local'
```

**Это ошибка восстановления текста декомпилятором, а не доказательство ошибки игрового скрипта во время работы.** Остальные специализированные контроллеры ведьмы — например, WitchLifeDrainController, WitchBreakNeckController и WitchPetrificationController — присутствуют с существенно более полным текстом.

Недочёт моего сборщика 1.1: успешный возврат непустой строки считался полученным исходником, даже если строка состоит из комментария об ошибке. В этом разборе такие результаты выделены отдельно. Проверка только `pcall` недостаточна; при дальнейшей доработке стоит добавлять отдельный статус для диагностического текста декомпилятора. Простое наличие слова Error в произвольном исходнике ошибкой считать нельзя.

## 3. Сетевая архитектура: старые и новые пути сосуществуют

Источник: `ReplicatedStorage.Shared.Modules.NetworkRegistry`.

Модуль описывает две группы:

| Группа | Папки |
|---|---|
| Network | `ReplicatedStorage.Network.Combat`, `Abilities`, `Systems`, `Functions` |
| Legacy | `ReplicatedStorage.Funções.Eventos`, `ReplicatedStorage.ArczisCombat.Remotes`, `ReplicatedStorage.Remotes` |

`GetEvent` и `GetFunction` получают объекты из Network и проверяют класс. `GetLegacyCombat` сопоставляет имя действия с объектом в старых папках.

### Подтверждённый пример разделения направления

В `WitchLifeDrainController`:

- Запрос клиента направлен к `Network.Combat.WitchLifeDrainRequest`, найденному через NetworkRegistry.
- Ответы клиент слушает через `Funções.Eventos.WitchLifeDrainRemote`.
- В обработчике ответов встречаются состояния `Started` и `Rejected`.

Таким образом, похожие названия в двух папках **не обязательно означают два взаимозаменяемых способа вызвать одну функцию**. Один объект может принимать запрос, а другой — передавать результат или состояние.

В `ArczisCombatController` основная боевая логика напрямую использует старую папку `ArczisCombat.Remotes`: CombatEvent, BlockEvent и ClashEvent. Это видно в самом клиентском коде, а не выведено из названий объектов.

**Серверные обработчики в этих отчётах отсутствуют.** Нельзя подтвердить серверную проверку дальности, расход ресурсов, выдачу наград или полномочия на административные действия. Никакие remotes при анализе не вызывались.

## 4. Боевая система

Источники: `ReplicatedStorage.ArczisCombat.CombatConfig` и `PlayerScripts.ArczisCombatController`.

### Значения в конфиге

| Параметр | Значение |
|---|---:|
| M1Damage | 8 |
| HeavyDamage | 20 |
| M1StaminaCost | 12 |
| HeavyStaminaCost | 35 |
| MinStaminaToAct | 15 |
| M1Cooldown / M1AnimationLock | 0,18 / 0,58 |
| HeavyCooldown / HeavyAnimationLock | 1,2 / 0,72 |
| HitboxSize | 7 × 7 × 7 |
| M1HitboxDelay / HeavyHitboxDelay | 0,24 / 0,42 |
| GuardBreakStunDuration | 1,5 |

Клиентский контроллер читает `Stamina` и проверяет атрибуты `ActionLocked`, `Hibernating`, `Ragdolled`. В запросе обычной атаки фигурирует серверное время, полученное через `workspace:GetServerTimeNow()`.

**Важно:** `M1Cooldown = 0.18` не доказывает возможность результативно атаковать каждые 0,18 секунды: отдельно существуют animation lock, состояния персонажа и неизвестные нам серверные проверки. Наличие параметров Heavy в конфиге также само по себе не доказывает доступность каждого тяжёлого действия в текущем интерфейсе.

Модуль содержит формулы Clash:

- Вес нажатия: `clamp(1 + max(0, level) / 250, 1, 4)`.
- Начальное преимущество: `clamp((max(0, levelA) - max(0, levelB)) * 0.01, -8, 8)`.

Это формулы общего модуля. Где и с какими данными сервер использует их, по клиентскому дампу полностью не установлено.

## 5. Способности и ограничения

### BloodDrinkConfig

В конфиге заданы `Cooldown = 8`, `MaximumDistance = 8`, `BloodGain = 40`, `TargetDamage = 15`, `NPCHitXP = 3`, `PlayerHitXP = 5`. Есть отдельные параметры истощения вампиров и отравления CannibalRaised. Эти числа нельзя автоматически переносить на все типы целей и состояния без серверной реализации.

### BatFormConfig — важная деталь

В полученном модуле **`Enabled = false`**, хотя остальные параметры формы присутствуют: UnlockYears 300, Cooldown 300, Duration 40, FlightSpeed 52.

Это полезная точка проверки при вопросе «почему нет формы летучей мыши». Но состояние одного общего конфига ещё не устанавливает поведение всей серверной реализации.

### CeilingSleepConfig

В конфиге сна под потолком: MinimumYears 100, FarmXPRewardInterval 30, FarmXPBaseAmount 28, FarmXPMaxAmount 56, FarmXPMaxScalingYears 800. Формула масштабирования и фактическая выдача XP сервером здесь не представлены.

## 6. Квесты: теперь есть реальные клиентские состояния

Получены `QuestClient`, `HunterQuestClient`, `Quest2Client`, `CorpseDeliveryQuestClient`, `HumanSideQuestClient`.

### Quest2Client

Трекер читает атрибуты игрока:

- `Quest2Active`, `Quest2Title`, `Quest2Description`;
- `Quest2Progress`, `Quest2Required`;
- `Quest2RewardXP`, `Quest2RewardMoney`, `Quest2TargetName`.

Объект предложения использует `Quest2Enabled`, `Quest2MinLevel`, `Quest2OfferId`, `Quest2Title`, `Quest2Description`, `Quest2XP`, `Quest2Money`, `Quest2Range`.

При штатном нажатии Accept клиент передаёт объект предложения и его идентификатор. Интерфейс блокирует принятие при активном Quest2, Quest или HumanSideQuest. Это подтверждает **клиентскую** проверку, но не описывает серверную валидацию.

### HumanSideQuestClient

Клиент обрабатывает ветку `WhiteFlowers` и доставку потерянного груза. В коде присутствуют состояния/сообщения `Offer`, `Started`, `FlowerProgress`, `FlowersReady`, `Carrying`, `GiverLost`, `Completed`, `Message`.

Для потерянного ящика предусмотрен поиск объекта в `Workspace.HumanSideQuestBoxes`; имя связано с UserId игрока. Это указывает на персонализированную цель квеста, а не просто любой ящик карты.

### CorpseDeliveryQuestClient

Используются атрибуты `CarryingQuestBody`, `CorpseQuestStage`, `CorpseQuestLoaded`, а для объектов тел — `CorpseQuestOwnerUserId` и `CorpseQuestBodyStatus`. Контроллер различает владельца и состояние тела.

## 7. Магазин и инвентарь

Получены `NPCShopClient` и `GameInventoryController`.

NPCShopClient читает `ShopItemName`, `ShopKind`, `BasePrice`, `ShopAvailable`, а также `Years` игрока. В штатном UI покупки различных категорий разделены; для метлы используется BroomRemote, для ряда других товаров — ShopRemote.

**Отображаемая клиентом цена и наличие кнопки не доказывают принятие покупки сервером.** Из этого кода нельзя сделать вывод о возможности бесплатной покупки или произвольного изменения стоимости.

## 8. Что находится в архиве

`Исходники_и_индекс_v1.1.zip` содержит:

- **234 уникальных `.lua`** с текстом декомпиляции без редактирования;
- **1 `.txt`** с уникальным сообщением об ошибке, соответствующим двум контроллерам;
- `manifest.json`: профиль, путь и ID каждой исходной записи, контрольная сумма текста, имя извлечённого файла;
- `index.md`: список текстов с количеством совпадающих копий;
- `remote_usage.csv`: текстовые совпадения FireServer, InvokeServer и OnClientEvent с номером строки и путём скрипта;
- `not_extracted.json`: две записи серверных Script без исходников.

`remote_usage.csv` — **статический указатель по тексту**, не перехват сетевого трафика, не полный протокол и не готовые команды для повторного запуска. Имена переменных в нём могут требовать чтения контекста соответствующего скрипта.

Файлы предназначены для чтения. Декомпилированные модули не выполнялись; синтаксическая и поведенческая корректность каждого текста не подтверждена. Полный аудит всех 234 уникальных текстов не проводился.

## 9. Что делать дальше

Повторять широкий сбор сейчас не нужно: для статического анализа основных клиентских систем материалов уже достаточно.

Полезный следующий шаг — выбрать конкретную задачу: диагностика квестовых состояний, отображение параметров способностей, разбор условий блокировки боя или объяснение работы определённого контроллера. Для двух повреждённых PowerController потребуется отдельная повторная декомпиляция или другой декомпилятор; повышение лимитов сборщика эту ошибку не исправляет.

Все выводы относятся к версии места 2812 и доступной клиенту выборке. Серверная реализация, будущие изменения игры и незагруженные StreamingEnabled-объекты остаются за пределами этого анализа.
